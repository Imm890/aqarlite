# عقارلايت — لبيع الوحدات العقارية

نظام متعدد الشركات (Multi-tenant) لبيع الوحدات العقارية بالتقسيط:
**حجز 72 ساعة ← مسودة عقد ← اعتماد المحاسب ← جدول أقساط تلقائي ← تسجيل دفعات وتوزيعها.**

Tech:
Backend: Node-js
Fronend: Next-js
Database: PostgreSQL
Container: Docker
---

## 1) التشغيل      

المتطلبات: Node.js ≥ 20.9، وPostgreSQL 16 (أسهلها Docker).

```bash
git clone <repo> aqarlite && cd aqarlite
npm ci

docker compose up -d db          # PostgreSQL 16 على 127.0.0.1:5432 + قاعدتا aqarlite و aqarlite_test
cp .env.example .env             # عدّل القيم (انظر الملاحظات أدناه)

npm run db:migrate               # ينشئ المخطط + دور التطبيق aqarlite_app ويضبط كلمة مروره
npm run db:seed                  # شركتان تجريبيتان
npm run dev                      # http://localhost:3000
```

إنتاجياً: `npm run build && npm start` (يتطلب `NODE_ENV=production`، فتصبح الكوكيز `Secure` و`__Host-` تلقائياً، ويجب أن يعمل خلف HTTPS).

> **مهم:** التطبيق يتصل بقاعدة البيانات بدور `aqarlite_app` (`DATABASE_URL`)، بينما يستخدم `DATABASE_ADMIN_URL` سكربتا الـ migration/seed فقط. يرفض التطبيق العمل إن اتصل بدور superuser أو مالك الجداول أو `BYPASSRLS` (انظر قسم العزل).

### حسابات الـ seed
كلمة المرور لكل الحسابات = قيمة `SEED_PASSWORD` في `.env` (الافتراضية في `.env.example`: `Demo-Passw0rd-2026!`، غيّرها). إن تركتها فارغة تُولَّد عشوائياً وتُطبع مرة واحدة.

| الشركة | الدور | البريد |
|---|---|---|
| شركة الأفق العقارية (SAR) | مدير الشركة | `admin@ofuq.example` |
| | محاسب | `accountant@ofuq.example` |
| | مندوب 1 / 2 | `rep1@ofuq.example` / `rep2@ofuq.example` |
| شركة النخبة للوساطة (AED) | مدير الشركة | `admin@nokhba.example` |
| | محاسب | `accountant@nokhba.example` |
| | مندوب 1 / 2 | `rep1@nokhba.example` / `rep2@nokhba.example` |

لكل شركة 12 وحدة (مشروعان) و6 عملاء (3 لكل مندوب).

## 2) القرارات التقنية (ولماذا، وما البديل المرفوض)

| القرار | السبب | البديل المرفوض |
|---|---|---|
| **المبالغ `BIGINT` بالهللات** في القاعدة والكود وJSON | دقة تامة؛ مجموع الأقساط = السعر النهائي حتى آخر هللة؛ لا أخطاء تقريب | `NUMERIC` (يُغري بتحويله لـ float في JS)، أو `float` |
| **عزل الشركات بثلاث طبقات**: شروط في الخدمات + RLS في PostgreSQL + مفاتيح أجنبية مركّبة | خطأ في طبقة واحدة لا يكفي لتسريب بيانات (التفاصيل في قسم الأمان) | فلترة بالتطبيق فقط (نسيان `WHERE` واحد = تسريب) |
| **جلسات من جهة الخادم** (جدول `sessions`، تجزئة SHA-256 للرمز) | إبطال حقيقي عند الخروج، وإبطال فوري لو عُطّل المستخدم | JWT (لا يُبطل قبل انتهائه) |
| **SQL خام عبر `pg` مع معاملات مرتبطة** | تحكم كامل بالأقفال والمعاملات؛ لا `ORM` يخفي ما يُنفَّذ | ORM (أصعب في ضمان ترتيب الأقفال وRLS) |
| **منطق الأقساط/الدفعات دوال نقية** في `src/domain` | اختبارها بلا قاعدة بيانات، وإعادة استخدامها (معاينة المسودة = نفس دالة الاعتماد) | منطق داخل route handler |
| **الحجز المتزامن: `SELECT … FOR UPDATE` على صف الوحدة** + فهرس فريد جزئي كخط دفاع أخير | المتسابق الثاني يُرفض برسالة واضحة (409) لا بخطأ 500 | `SERIALIZABLE` فقط (يتطلب إعادة محاولات وأخطاء أقل وضوحاً) |
| **انتهاء الحجز**: دالة SQL واحدة تُستدعى عند كل قراءة/كتابة تمس الوحدات + مهمة خلفية كل دقيقة | الصحة لا تعتمد على نجاح مهمة خلفية؛ لا تأخير ظاهر للمستخدم | `cron` خارجي فقط (نافذة تأخر) |
| **حالة `overdue` مشتقة وقت القراءة** ولا تُخزَّن | لا تصبح قديمة أبداً ولا تحتاج مهمة تحديث | عمود مخزَّن + job |
| **المصادقة الخاصة**: دوال `SECURITY DEFINER` ضيقة؛ التطبيق لا يملك صلاحية على `sessions` ولا على `password_hash` | سرقة حقن SQL افتراضية لا تكشف التجزئات | إعطاء `SELECT` على `users` كاملاً |

بنية الشيفرة: `src/domain` (نقي) ← `src/server/services` (معاملات وقواعد) ← `src/app/api` (غلاف رفيع: CSRF → جلسة → دور → Zod → خدمة) ← `src/app/(app)` (واجهة).

## 3) الافتراضات (قواعد غامضة وكيف قررت)

1. **تاريخ بداية العقد** = تاريخ استحقاق الدفعة الأولى، والقسط k يستحق بعد k شهراً من تاريخ البداية **الأصلي** (لا من القسط السابق): 31 يناير ← 28/29 فبراير ← **31 مارس** ← 30 أبريل (بلا انجراف). يُقيَّد بين اليوم وسنة قادمة.
2. **الدفعة الأولى** تُسجَّل كبند رقم 0 في جدول الأقساط (يُسدَّد بالطريقة نفسها)، ويجوز أن تكون صفراً (فلا بند). يجب أن تكون أقل من السعر النهائي.
3. **الباقي من القسمة** يُوزَّع هللة هللة على أول الأقساط (الفرق بين أي قسطين ≤ هللة واحدة).
4. **الخصم**: `السعر النهائي ≥ 95% من سعر الوحدة` بحساب صحيح، ولا يزيد على سعر الوحدة. سعر الوحدة يُثبَّت في العقد وقت الإنشاء.
5. **المسودة** تبقى مرتبطة بالحجز؛ إن انتهى الحجز (72 ساعة) قبل الاعتماد **تُلغى المسودة تلقائياً** وتعود الوحدة متاحة. المندوب يستطيع إلغاء مسودته يدوياً (فيبقى الحجز نشطاً حتى انتهائه).
6. **جدول الأقساط يُحفظ عند الاعتماد** (المسودة تعرض معاينة محسوبة بالدالة نفسها)، فلا تتغير الأقساط بعد الاعتماد.
7. **مدير الشركة** يقرأ كل عملاء وحجوزات وعقود شركته (قراءة فقط)، ولا يحجز ولا يعتمد (فصل المهام). **المحاسب** يقرأ كل العقود لكن لا يقرأ العملاء مباشرة.
8. **المندوب يحجز لعميله فقط**، وعميل مندوب آخر يُعامل كغير موجود (404) لا ممنوع، فلا يُكشف وجوده. الأمر نفسه عبر الشركات.
9. **التوزيع على الأقدم أولاً** = حسب تاريخ الاستحقاق ثم التسلسل. الدفعة **لا تُجزَّأ ولا تُرفض جزئياً**: إما تُقبل كاملة أو تُرفض إن تجاوزت المتبقي.
10. **منع التكرار**: مفتاح `idempotencyKey` تولّده الواجهة لكل نية دفع. نفس المفتاح + نفس المحتوى = نفس الدفعة (200 بدل 201)، ونفس المفتاح + محتوى مختلف = 422.
11. **اليوم** (لحالة `overdue` ولتقييد تاريخ البداية) بتوقيت الشركة (`companies.timezone`)، والقسط متأخر **بعد** يوم استحقاقه.
12. **لا حذف** لأي سجل أعمال (تُمنع بالصلاحيات والمحفّزات)؛ الإلغاء حالة.
13. **الحد من التخمين**: 8 محاولات فاشلة لكل بريد خلال 15 دقيقة (و30 لكل IP عند وجود وسيط موثوق). مقايضة معروفة: يمكن لمهاجم أن يقفل حساب ضحية مؤقتاً؛ فضّلته على السماح بالتخمين. يُحتسب البريد غير الموجود أيضاً فلا يكشف الرد وجوده.
14. **العملة** لكل شركة (SAR/AED) للعرض فقط؛ لا تحويل عملات.

## 4) الأمان

### كيف يُضمن عزل الشركات (Tenant Isolation)
`company_id` **يؤخذ من الجلسة في الخادم حصراً**، ولا يقبله أي endpoint من الجسم أو الاستعلام أو المسار (مخططات Zod من نوع `strictObject` ترفض أي حقل زائد بـ 422، فحقن `companyId` يفشل).

1. **طبقة التطبيق** — `apiRoute()` تحلّ الجلسة من الكوكي في قاعدة البيانات، وتبني `AuthContext {userId, companyId, role}`، وتمرّره للخدمات. كل خدمة تعمل عبر `withTenant(ctx, fn)` وكل استعلام فيها يقيّد بـ `company_id = $ctx.companyId` (ومعه `owner_id`/`rep_id` للمندوب).
2. **طبقة قاعدة البيانات (RLS)** — `withTenant` يفتح معاملة ويضبط `set_config('app.company_id', <من الجلسة>, true)` (محلي للمعاملة فلا يتسرب بين الطلبات). على كل جدول أعمال سياسة `company_id = app_tenant()` للقراءة والكتابة (`USING` و`WITH CHECK`). **بلا ضبط الشركة = صفر صفوف** (إغلاق آمن). حتى لو نسي مطوّر شرط `WHERE` فلن يرى إلا شركته.
   - دور التطبيق `aqarlite_app` بلا `SUPERUSER` ولا `BYPASSRLS` وليس مالك الجداول، **ويرفض `withTenant` العمل** إن اتصل بدور يتجاوز RLS (فحص عند أول استخدام).
   - صلاحيات أقل ما يلزم: لا `DELETE` في أي مكان، ولا `UPDATE` على الدفعات/التدقيق، ولا وصول لـ `password_hash` أو `sessions`.
3. **طبقة المخطط** — مفاتيح أجنبية **مركّبة** `(company_id, id)`: لا يمكن حتى لمسؤول قاعدة البيانات ربط عميل شركة بمندوب شركة أخرى (مُختبَر).
4. **الاختبار** — `tests/integration/tenant-isolation.test.ts`: مستخدم شركة "النخبة" يهاجم بيانات "الأفق" عبر المعرّفات المباشرة وحقن `companyId` والبحث والحجز المتقاطع والدفع والتدقيق، وكل ذلك 404/422، مع اختبارات RLS على مستوى SQL.

### أهم 3 مخاطر محتملة وكيف عولجت

**① كسر عزل الشركات / الوصول لسجل ليس لك (IDOR وBOLA).** أخطر خطر في نظام متعدد المستأجرين: معرّف UUID لسجل شركة أخرى يكفي لقراءته إن غاب شرط واحد.
*المعالجة:* ثلاث طبقات مستقلة (القسم أعلاه)؛ التحقق من الدور **والملكية** في كل endpoint داخل الخادم؛ سجل غير مملوك = 404؛ `strictObject` ضد mass assignment (لا يمكن للمندوب إرسال `status` أو `ownerId` أو `approvedBy` أو `recordedBy`)؛ معرّفات المسار تُتحقق كـ UUID قبل أي استعلام. اختبارات: عزل الشركات + مصفوفة RBAC + mass assignment.

**② اختلال سلامة البيانات المالية (سباقات وتكرار وتعديل).** حجز مزدوج لوحدة، أو دفعتان بالضغط المزدوج/إعادة إرسال الشبكة، أو دفعات متزامنة تتجاوز المتبقي، أو تعديل عقد/دفعة بعد تسجيلها.
*المعالجة:* قفل صف الوحدة `FOR UPDATE` وفهرس فريد جزئي (حجز نشط واحد/وحدة)؛ قفل العقد وأقساطه عند الدفع بترتيب أقفال ثابت (وحدة ← حجز ← عقد ← أقساط)؛ مفتاح idempotency فريد لكل شركة؛ **كل عملية مالية في معاملة واحدة** (اعتماد = وحدة+حجز+عقد+أقساط+تدقيق)؛ في القاعدة: محفّزات تمنع تعديل العقد المعتمد والدفعات والتدقيق وحذفها، وقيود `CHECK` (خصم ≤ 5%، 72 ساعة، `paid ≤ amount`)، وفحوص مؤجلة تضمن أن مجموع الأقساط = السعر النهائي ومجموع التوزيع = مبلغ الدفعة. اختبارات متزامنة حقيقية (30 حجزاً متزامناً ← ينجح واحد؛ 10 دفعات متزامنة ← لا يتجاوز المتبقي؛ نفس المفتاح × 10 ← دفعة واحدة).

**③ سرقة الجلسات والتخمين وCSRF/XSS (المهاجم مستخدم مسجّل).**
*المعالجة:* كلمات المرور Argon2id (19 MiB, t=2) ولا تظهر في أي استجابة أو سجل (محجوبة آلياً في اللوجر)؛ الكوكي `HttpOnly` + `Secure` + `SameSite=Strict` + بادئة `__Host-` ولا شيء في `localStorage`؛ الرمز عشوائي 256 بت وفي القاعدة تجزئته فقط؛ الخروج يضع `revoked_at` في الخادم (مُختبَر: نفس الكوكي بعد الخروج = 401)؛ مهلة خمول ومهلة مطلقة؛ رسالة دخول موحّدة ومعادلة زمنية بتجزئة وهمية فلا يُكشف وجود البريد؛ حد تخمين؛ CSRF بفحص `Origin` وSec-Fetch-Site وJSON فقط وSameSite؛ XSS: React يرمّز كل المخرجات ولا `dangerouslySetInnerHTML` في المشروع، وCSP صارمة بـ nonce لكل طلب (بلا inline scripts/styles)، وتنظيف محارف التحكم من المدخلات؛ SQL: **معاملات مرتبطة فقط** وأعمدة الترتيب من قائمة بيضاء ثابتة، وأنماط `LIKE` تُهرَّب.

### إجراءات أخرى
- ترويسات: CSP (nonce)، HSTS، `X-Frame-Options: DENY`، `nosniff`، `Referrer-Policy: no-referrer`، COOP/CORP، `Permissions-Policy`؛ ولا `X-Powered-By`.
- رسائل الأخطاء عامة وعربية مع `requestId`؛ التفاصيل (SQLSTATE، المكدّس) في سجلات الخادم JSON فقط. أخطاء القيود تُحوَّل لرسائل عامة آمنة.
- تحقق صارم بـ Zod لكل مدخل بما فيها الفلترة والترتيب والترقيم (أعداد صحيحة فقط، حدود قصوى، رفض المعاملات المكررة والمجهولة).
- الأسرار في متغيرات البيئة فقط (`.env` في `.gitignore`، و`.env.example` بقيم وهمية)؛ لا أسرار في الواجهة ولا في تاريخ git.
- `npm audit`: **0 ثغرات** (`npm run audit:prod` يفشل عند high/critical).
- **سجل التدقيق** (للإضافة فقط، يقرأه المدير لشركته): دخول فاشل/ناجح/خروج، إضافة وحدة، **تغيير سعر (القديم والجديد)**، حجز، إنشاء/إلغاء عقد، **اعتماد العقد**، **تسجيل الدفعة**؛ يُكتب داخل معاملة العملية نفسها (لا عملية بلا أثر ولا أثر بلا عملية).

## 6) ما لم يُنجز (بصراحة) وكيف كنت سأنفّذه

- **مصادقة ثنائية (2FA) وقفل متدرّج للحساب وإشعار المستخدم**: كنت سأضيف TOTP وتأخيراً تصاعدياً بدل القفل الثابت.
- **إدارة المستخدمين وتغيير كلمة المرور**: خارج النطاق المطلوب (لا شاشة مستخدمين)؛ تُدار حالياً عبر SQL/seed. كنت سأضيف تدوير الجلسات عند تغيير كلمة المرور.
- **حد معدّل عام (rate limiting) على بقية الـ API**: الدخول محمي فقط. كنت سأضيف حداً لكل مستخدم عبر Redis أو في بوابة (reverse proxy).
- **سجل التدقيق لا يُسجّل القراءات/الاستعلامات الممنوعة (403)**؛ كنت سأضيف حدث `ACCESS_DENIED`.
- **سجل التدقيق قابل للتلاعب من مسؤول قاعدة البيانات الأعلى (superuser)**: الحماية بالمحفّزات والصلاحيات؛ للمتطلبات التنظيمية كنت سأضيف تسلسلاً تجزيئياً (hash chain) وشحناً لمخزن غير قابل للتعديل (WORM).
- **اختبارات واجهة آلية (E2E) في CI**: أجريتها يدوياً بـ Playwright ولم أحوّلها لمجموعة اختبارات مُلتزمة.
- **مراقبة وتتبع**: لوجات JSON جاهزة، لكن بلا metrics/Alerting.
- **انتهاء الحجوزات في بيئة متعددة النسخ**: الدالة آمنة للتزامن (`SKIP LOCKED`)، لكن مهمة الدقيقة تعمل في كل نسخة؛ كنت سأنقلها لـ pg_cron أو worker واحد.
- **الإلغاء بعد الاعتماد/استرداد الدفعات**: غير مطلوب؛ يتطلب قيوداً محاسبية (قيود عكسية) لا تعديلاً.
- **إمكانية الوصول (a11y)**: أسس جيدة (تسميات، `aria`, تركيز بعد النوافذ) لكن بلا تدقيق كامل بقارئ شاشة.

## 7) أدوات الذكاء الاصطناعي
بُني هذا المشروع بمساعدة **Claude (Anthropic)** عبر Claude Code: تصميم البنية، كتابة المخطط والخدمات والواجهة والاختبارات، وتشغيل الاختبارات والبناء وفحص الواجهة في متصفح فعلي.
